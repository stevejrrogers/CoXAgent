# Deploy Secret Rotation Stability (CXA-B027)

**Keywords:** deploy secrets, secret rotation, PG_PASSWORD, COXAGENT_ADMIN_PASSWORD, stable secrets, durable store, pgdata volume auth failure, admin login broken, unconfigured deploy, resolve_deploy_secrets

## Overview

CXA-B027 is the incident report behind "auto-generated deploy secrets rotate every cycle." For an app-driven deploy where no operator configured `PG_PASSWORD` / `COXAGENT_ADMIN_PASSWORD`, each cycle minted a *fresh* random fallback secret. Postgres initialises its named data volume with cycle N's value; cycle N+1 then boots with a regenerated one — so DB auth fails and admin login breaks on an already-initialized database. This page documents that failure and how later tickets (B028/B031/B032/B036/B039/B040) made fallback secrets **stable across cycles** without ever persisting them into the source tree. It is for anyone working on the docker-compose deploy adapter or diagnosing DB/admin auth failures on agent-deployed stacks.

## How it works

The whole flow lives in `crates/infrastructure/src/deploy/docker_compose.rs`. Each pass calls `DockerComposeDeploy::deploy(work_dir)`:

1. Recognises a compose file among `COMPOSE_FILES`, names the project via `compose_project_name()` (`cox-<parent>-<dir>`, sanitised), and evicts any stale project squatting its ports.
2. Calls `resolve_deploy_secrets(work_dir)` once per pass — computed ONCE so a port-eviction retry re-runs identical interpolation.
3. Feeds results through `seed_deploy_secrets()` into both the initial `docker compose up -d --build` command and any retry.

`resolve_deploy_secrets` → `resolve_deploy_secrets_in(work_dir, secret_root)` applies this precedence per key in `REQUIRED_SECRET_KEYS = ["PG_PASSWORD", "COXAGENT_ADMIN_PASSWORD"]`:

1. **Process env** — a non-blank value leaves that key alone (the closure passed to `missing_required_secrets`).
2. **Project-dir `.env`** — a non-blank assignment parsed by `read_dot_env()` leaves it alone.
3. **Fallback (the B027 path)** — only keys missing from both get a value: read back from this project's *durable out-of-tree store*, or freshly generated by `random_secret()` and persisted there.

The durability machinery that closes B027:

- **Out-of-tree store**: values persist under `${COXAGENT_DEPLOY_SECRETS_DIR}` (default `<HOME>/.local/share/coxagent/deploy-secrets`) as `<digest>.env`, written atomically via temp-sibling + rename (`persist_store`) and hardened to owner-only (`set_secret_perms`, 0o600). Never written into `<project>/codebase/.env`.
- **Store key = compose project name**, not disk path (`store_file()`, SHA-256 of `compose_project_name`) — because docker persists pgdata in a NAMED volume keyed by that same project name (`<project>_db`), which survives re-clones and relocations (CXA-B032).
- **Legacy adoption**: an older path-keyed store file (`cxb031_store_file`) is merged via `adopt_legacy_cxb031_secrets()`, recovering exactly what initialised pgdata during an upgrade window (CXA-B036/B039), gated by an ownership stamp so one project can't adopt another's credentials (CXA-B043).
- **Expiry ordering**: legacy files are deleted only *after* their values are durably persisted to the canonical store (`expire_converged_legacy_store`, CXA-B044).

Admin login connects here because when RBAC runs local mode (`build_auth()` in crates/app/src/builders.rs), it provisions an admin from env: users keep whatever password first booted them while per-cycle regeneration supplied inconsistent values over time against an initialized DB/pgdata.

## Usage

There is no user-facing flag; stability is automatic inside every app-driven deploy once any required secret is absent everywhere.

```sh
# Point resolution at an isolated store to watch it work without touching HOME:
export COXAGENT_DEPLOY_SECRETS_DIR=/tmp/demo-secrets
cd <an-unconfigured-project-with-a-compose-file>

# Run two deploy cycles; inspect what got stored out of tree:
ls -la "$COXAGENT_DEPLOY_SECRETS_DIR"
cat "$COXAGENT_DEPLOY_SECRETS_DIR"/*.env   # first line "# owner=..." then KEY=VALUE lines
```

To pin your own credentials instead of relying on generated/stored ones:

```bash
export PG_PASSWORD='your-pg-secret'
export COXAGENT_ADMIN_PASSWORD='your-admin-secret'
coxagent <deploy-driving command> <project>

# or place both in <project-dir>/.env:
#   PG_PASSWORD=your-pg-secret
#   COXAGENT_ADMIN_PASSWORD=your-admin-secret
```

An operator-supplied value always wins verbatim; nothing seeds/resolves for keys you supply.

## Interface

All identifiers live in crates/infrastructure/src/deploy/docker_compose.rs unless noted:

- const REQUIRED_SECRET_KEYS = ["PG_PASSWORD", "COXAGENT_ADMIN_PASSWORD"]
- fn random_secret() -> String — 32 chars from a charset that drops look-alikes (`0/O/1/l/I`) and YAML/DSN-breaking characters; never baked constants
- fn resolve_deploy_secrets(work_dir: &Path) -> Vec<(String,String)>
- fn resolve_deploy_secrets_in(work_dir: &Path, secret_root: &Path) -> Vec<(String,String)> — single-pass decision + persist + legacy adoption/expiry
- fn missing_required_secrets(provided_by_env: impl Fn(&str)->bool, dot_env_keys: &HashSet<String>) -> Vec<&'static str> — pure precedence rule
- fn seed_deploy_secrets(cmd: &mut tokio::process::Command, secrets: &[(String,String)])
- fn read_dot_env(path) -> HashSet<String>, read_stored_secrets(path) -> HashMap<String,String>, read_owner_stamp(path) -> Option<String>
- fn store_file(secret_root, work_dir) / cxb031_store_file(...) -> PathBuf — current vs legacy key derivation
- fn adopt_legacy_cxb031_secrets(...) -> bool; retire_superseded_path_keyed_store(...); expire_converged_legacy_store(path)
- fn write_stored_secrets_owned(path, owner: Option<&str>, secrets) -> bool; persist_store(...); set_secret_perms(path); repair_store_permissions(...)
- fn compose_project_name(work_dir) -> String
- Consumers of resolve+seed: DockerComposeDeploy::deploy() (initial up + port-eviction retry) and compose_build_check()

RBAC link (crates/app/src/builders.rs): build_auth() reads COXAGENT_ADMIN_USER / COXAGENT_ADMIN_PASSWORD to bootstrap_admin(...).

## Configuration

| Setting | Default | Effect |
|---|---|---|
| Required key present in process env OR project-dir `.env` | n/a | Honoured verbatim; never overridden or poisoned |
| Required key absent everywhere | n/a | Stable stored value reused; minted once then persisted out-of-tree |
| COXAGENT_DEPLOY_SECRETS_DIR | `<HOME>/.local/share/coxagent/deploy-secrets` (falls back to temp dir when HOME unset) | Root directory for durable per-project fallback stores; tests/sandboxes point this at isolated dirs |
| Store file permissions | 0o600 after write / repair | Credentials at rest are owner-only |
| Store file ownership stamp | first line "# owner=<compose-project-name>" | Refuses adoption of credentials authored by another project sharing this dir |

No CLI flags or config-file knobs were added for B027 itself; behaviour is entirely driven by which values are present plus these env settings.

## Edge cases and limits

What this deliberately does NOT do:

- It never writes generated secrets back into `<project>/codebase/.env` or anywhere inside the source tree agents read diffs from / commit from (CXA-B028 guard).
- It does not rotate per cycle when nothing is configured.
- It does not clobber operator-configured values.
- It will not adopt or delete a legacy store owned by a differently-named project sharing this directory.

How it fails / known limits:

- Store persistence is best-effort ([CXA-B044]): if atomic rename fails before completion it returns non-durable so no partial content lingers; callers treat non-true as "nothing durable exists yet".
- Legacy deletion happens only after durable persist succeeds; otherwise the old file stays so next pass re-adopts rather than losing both stores.
- Keying follows docker's named-volume semantics via basenames only (`cox-parent-dir`) — genuinely distinct projects keep separate files even when base dirs resemble each other.
- If every required secret resolves externally resolution returns early with nothing seeded — correct because no fallback was needed (superseded stores are still retired via retire_superseded_path_keyed_store).

## Code map

- crates/infrastructure/src/deploy/docker_compose.rs — DockerComposeDeploy adapter body containing all resolution/persistence logic above plus deploy(), compose_project_name(), apply_resource_limits(), running_services() and the port-eviction helpers extract_bind_port / compose_project_on_port / container_on_port / evictable_project(). The unit-test module mod deploy_secret_tests (~line 1713) carries the regression guards for this ticket chain: precedence/baked constants/charset/.env parsing (B017), generated_secrets_are_stable_across_cycles_for_the_same_project (B031), secrets_survive_relocating_the_app_between_paths (B032), pre-CXA-B032 adoption (B036), divergent-intervening-value recovery (B039), superseded-store retirement even when no fallback is needed (B040) and resolving_deploy_secrets_never_persists_them_to_work_dir_dot_env (B028).
- crates/app/src/builders.rs — build_auth() reads COXAGENT_ADMIN_USER / COXAGENT_ADMIN_PASSWORD and calls FileAuthService::bootstrap_admin(...) / SqlAuthService::bootstrap_admin(...); the admin-login half of the ticket.
- crates/infrastructure/src/auth.rs — FileAuthService::bootstrap_admin(path, username, password) persists the admin account into auth.json; the counterpart that must agree with whatever stable password a deploy seeds.
- crates/app/tests/compose_security_gate.rs — guards compose interpolation/security behaviour around `${VAR}` usage for these required keys.
- crates/app/tests/committed_secrets_gate.rs — anti-regression gate preventing committed source/literals from carrying ADMIN_PASSWORD-style values again.
- crates/app/tests/deploy_smoke.rs — boot-level smoke test of this repo's own compose stack.
